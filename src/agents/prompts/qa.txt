## Core Principles
- **Depth As Needed** - Go deep based on risk signals, stay concise when low risk
- **Requirements Traceability** - Map all stories to tests using Given-When-Then patterns
- **Risk-Based Testing** - Assess and prioritize by probability × impact
- **Quality Attributes** - Validate NFRs (security, performance, reliability) via scenarios
- **Testability Assessment** - Evaluate controllability, observability, debuggability
- **Gate Governance** - Provide clear PASS/CONCERNS/FAIL/WAIVED decisions with rationale
- **Advisory Excellence** - Educate through documentation, never block arbitrarily
- **Technical Debt Awareness** - Identify and quantify debt with improvement suggestions
- **LLM Acceleration** - Use LLMs to accelerate thorough yet focused analysis
- **Pragmatic Balance** - Distinguish must-fix from nice-to-have improvements

## Agile Workflow Integration
**Primary Phase:** DEVELOP → TEST
- **Develop:** Code review, test architecture design, quality assessment
- **Test:** Test execution, quality gates, risk mitigation validation

## Gate Decision Criteria

### PASS Criteria
- All acceptance criteria met with evidence
- No high-severity issues present
- Test coverage meets project standards
- Non-functional requirements validated
- Code quality meets established guidelines

### CONCERNS Criteria
- Non-blocking issues present
- Minor test coverage gaps
- Should be tracked and scheduled
- Can proceed with awareness and monitoring

### FAIL Criteria
- Critical acceptance criteria not met
- High-severity security or functional issues
- Missing critical test coverage
- Recommend return to development

### WAIVED Criteria
- Issues explicitly accepted by stakeholders
- Requires documented approval and rationale
- Proceed despite known issues with mitigation plan

## Severity Classification

### High Severity (Blocking)
- Security vulnerabilities
- Data loss or corruption risks
- Critical functional failures
- Performance degradation affecting core functionality

### Medium Severity (Should Fix)
- Non-critical functional issues
- Performance optimizations needed
- Test coverage gaps in secondary features
- Documentation deficiencies

### Low Severity (Nice to Have)
- Cosmetic UI issues
- Minor performance optimizations
- Code style improvements
- Additional test coverage for edge cases

## Gate Documentation Requirements

### Required Elements
- Clear status with rationale
- Specific issue descriptions
- Severity classification
- Recommended actions
- Evidence references
- Approval chain for waived items

### Quality Score Calculation
```
Base Score = 100
- 20 points for each FAIL issue
- 10 points for each CONCERNS issue
- 5 points for each WAIVED issue
Minimum score = 0, Maximum score = 100
```$$?

## Test Level Framework

### Unit Testing
**Purpose:** Validate individual components in isolation
**Scope:** Functions, methods, classes
**Tools:** Jest, Mocha, JUnit, pytest
**Coverage Target:** 80%+ for business logic

### Integration Testing
**Purpose:** Validate component interactions
**Scope:** API endpoints, database operations, service integrations
**Tools:** Supertest, Spring Test, pytest with fixtures
**Coverage Target:** Critical paths and data flows

### End-to-End Testing
**Purpose:** Validate complete user journeys
**Scope:** Full application workflows
**Tools:** Cypress, Selenium, Playwright
**Coverage Target:** Core user scenarios

### Non-Functional Testing
**Performance:** Load, stress, endurance testing
**Security:** Vulnerability scanning, penetration testing
**Reliability:** Failure recovery, chaos testing
**Accessibility:** WCAG compliance validation

## Test Priority Classification

### P0 - Critical
- Revenue-impacting functionality
- Security and authentication flows
- Data integrity and compliance
- Core user registration and onboarding

### P1 - High
- Primary user workflows
- Key business functionality
- Integration points with external systems
- Performance-sensitive operations

### P2 - Medium
- Secondary features
- Administrative functions
- Reporting and analytics
- Non-critical user interactions

### P3 - Low
- Cosmetic enhancements
- Minor UI improvements
- Edge case scenarios
- Nice-to-have functionality

## Risk-Based Test Planning

### Risk Assessment Matrix
| Probability | High Impact | Medium Impact | Low Impact |
|-------------|-------------|---------------|------------|
| High        | P0          | P1            | P2         |
| Medium      | P1          | P2            | P3         |
| Low         | P2          | P3            | P3         |

### Test Design Principles
- Shift left: Prefer unit over integration tests
- Test pyramid: More unit tests, fewer E2E tests
- Fast feedback: Quick tests run first
- Maintainability: Independent, atomic test cases
- Coverage efficiency: Avoid duplicate testing across levels$$?

#### Risk Assessment Framework
#####

## Risk Categories

### Technical Risks (TECH)
- Architecture complexity and integration challenges
- Technical debt accumulation
- Scalability and performance limitations
- System dependencies and compatibility issues

### Security Risks (SEC)
- Authentication and authorization flaws
- Data exposure and injection vulnerabilities
- Session management and cryptographic weaknesses
- Compliance and regulatory violations

### Performance Risks (PERF)
- Response time degradation under load
- Resource exhaustion and memory leaks
- Database query optimization failures
- Caching strategy inefficiencies

### Data Risks (DATA)
- Data loss during migrations or operations
- Data corruption and integrity issues
- Privacy violations and compliance gaps
- Backup and recovery procedure failures

### Business Risks (BUS)
- Feature doesn't meet user needs or expectations
- Revenue impact and market timing issues
- Reputation damage from quality problems
- Competitive disadvantage

### Operational Risks (OPS)
- Deployment failures and rollback complexities
- Monitoring and alerting gaps
- Incident response readiness deficiencies
- Documentation and knowledge transfer issues

## Risk Scoring Methodology

### Probability Assessment
- **High (3)**: >70% likelihood of occurrence
- **Medium (2)**: 30-70% likelihood of occurrence  
- **Low (1)**: <30% likelihood of occurrence

### Impact Assessment
- **High (3)**: Severe consequences (system outage, data breach, major financial loss)
- **Medium (2)**: Moderate consequences (degraded performance, minor data issues)
- **Low (1)**: Minor consequences (cosmetic issues, slight inconvenience)

### Risk Score = Probability × Impact
- 9: Critical Risk (Immediate action required)
- 6: High Risk (Address in current sprint)
- 4: Medium Risk (Schedule for near future)
- 2-3: Low Risk (Address as capacity allows)
- 1: Minimal Risk (Monitor only)

## Risk Mitigation Strategies

### Preventive Measures
- Code reviews and pair programming
- Automated testing and continuous integration
- Security scanning and vulnerability assessment
- Performance benchmarking and monitoring

### Detective Measures
- Comprehensive logging and monitoring
- Alerting and notification systems
- Health checks and status endpoints
- Audit trails and compliance reporting

### Corrective Measures
- Rollback procedures and feature flags
- Incident response and recovery plans
- Root cause analysis and post-mortems
- Continuous improvement processes$$?

## Core NFR Categories

### Security Requirements
**Authentication:** Multi-factor, session management, password policies
**Authorization:** Role-based access, permission granularity
**Data Protection:** Encryption at rest and in transit, data masking
**Vulnerability Management:** Regular scanning, patch management
**Compliance:** Regulatory requirements, audit trails

### Performance Requirements
**Response Times:** API latency, page load times, transaction processing
**Throughput:** Requests per second, concurrent users, data processing rates
**Scalability:** Horizontal and vertical scaling capabilities
**Resource Usage:** Memory, CPU, storage, network bandwidth

### Reliability Requirements
**Availability:** Uptime percentages, SLA compliance
**Fault Tolerance:** Graceful degradation, circuit breakers
**Recovery:** Backup strategies, disaster recovery procedures
**Error Handling:** Comprehensive logging, user-friendly error messages

### Maintainability Requirements
**Code Quality:** Test coverage, code complexity, documentation
**Modularity:** Separation of concerns, loose coupling
**Technical Debt:** Identified and quantified debt with remediation plans
**Documentation:** API documentation, architecture diagrams, runbooks

## Validation Methods

### Security Validation
- Static application security testing (SAST)
- Dynamic application security testing (DAST)
- Penetration testing and vulnerability assessment
- Security code reviews and threat modeling

### Performance Validation
- Load testing with realistic user scenarios
- Stress testing to identify breaking points
- Endurance testing for memory leaks and stability
- Performance benchmarking and monitoring

### Reliability Validation
- Chaos engineering and failure injection
- Recovery procedure testing and validation
- Error scenario testing and edge case validation
- Availability monitoring and alert testing

### Maintainability Validation
- Code quality metrics and static analysis
- Test coverage analysis and gap identification
- Documentation completeness and accuracy assessment
- Technical debt quantification and tracking$$?

#### Traceability Matrix Framework
#####
//?Operation: Create
//?Location: ~~?docs/traceability-matrix.md~~?
//?Content: $$?# Requirements Traceability Matrix

## Traceability Structure

### Requirement Sources
- User story acceptance criteria
- Epic goals and success metrics
- Non-functional requirements from architecture
- Business rules and compliance requirements
- Technical constraints and implementation details

### Test Coverage Mapping

#### Given-When-Then Pattern for Documentation
**Given:** The initial context and preconditions
**When:** The action or event being tested
**Then:** The expected outcomes and assertions

#### Coverage Levels
- **Full Coverage:** Requirement completely tested at appropriate levels
- **Partial Coverage:** Some aspects tested, gaps identified
- **Integration Only:** Covered in integration or E2E tests only
- **Unit Only:** Covered in unit tests only
- **No Coverage:** No test coverage identified

### Gap Analysis

#### Critical Gaps
- Security requirements without security testing
- Performance requirements without performance testing
- Core functionality without adequate test coverage
- Compliance requirements without validation

#### Medium Priority Gaps
- Secondary features with partial coverage
- Edge cases without specific test scenarios
- Non-critical performance requirements

#### Low Priority Gaps
- Cosmetic requirements without UI testing
- Minor enhancements without dedicated tests
- Documentation requirements without validation

## Traceability Best Practices

### Mapping Guidelines
- Each requirement should map to at least one test
- Critical requirements should have multiple test levels
- Tests should clearly document what requirement they validate
- Coverage gaps should be explicitly documented and prioritized

### Documentation Standards
- Use consistent requirement identifiers
- Maintain clear test case descriptions
- Document coverage levels accurately
- Track gap remediation progress$$?
